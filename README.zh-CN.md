# code-quality-workflows

**一个把「代码质量」当作纪律而不是清单的 Agent 技能——调试、测试、评审、重构、自食其力、分支维护，每一块都围绕真正会咬人的失败模式写。**

[English](README.md) · [技能定义](SKILL.md) · [参考文献](references/)

---

## 为什么有这个技能

给 Agent 的「软件质量」指导大多是一串动词：*写测试、做代码评审、经常重构*。这类建议无法被证伪，因此也没用——它不会告诉你，当测试本地通过、CI 失败时该干什么；也不会告诉你，当评审说「看着没问题」然后上线挂了时，问题出在哪一层。

这个技能按**失败模式**组织，而不是按活动组织。每一节回答三件事：这里会怎么坏、怎么尽早发现、晚发现的代价是多少。

```
朴素循环：  写代码 → 跑一下 → 看着没问题 → 上线 → 事故
纪律循环：  写代码 → 预测失败 → 证明它确实失败 → 修 → 证明它现在通过
```

差别不在工作量，而在**知道该往哪儿看**。

## 干了大半活的三个习惯

**1. 先让 bug 可复现，再动手修。**
无法先演示失败的修复只是猜测。写失败用例的成本，几乎总是低于「修了个假 bug、被回一句『还是坏的』」的成本。

**2. 能检查就别打印。**
`print()` 调试本质是二分——每一轮把未知空间砍一半。调试器或 REPL 直接跳到答案。技能里写了 Python / Node / Jupyter 的具体附加步骤，因为**搭建摩擦正是把人推回 `print()` 的原因**。

**3. 报告证据，不报告结论。**
「这应该能修好」不算交付。「这是失败用例、这是改动前的运行、这是改动后的运行、这是我唯一没覆盖到的一种情况」才算。

## 全流程项目体检

被要求评估整个代码库（而不是修一个 bug）时，工作流是广度优先、每一步刻意浅：

1. **入口** —— 实际会跑起来的东西（不是 README 声称的）
2. **边界** —— 不可信输入从哪进来、在那里做了什么校验
3. **错误路径** —— 网络、磁盘、依赖失败时会发生什么
4. **重复** —— 同一套逻辑在两处用不同方式实现了两遍
5. **死重** —— 永远走不到、但必须继续维护的代码

这些看完再谈风格。风格问题产出便宜、执行昂贵；漏掉的边界校验正好相反。

## 这个技能要防的坑

- **修用户报告的症状**，而不是产生症状的那个条件
- **把绿的测试当作正确性证明**，而测试从未走过失败路径
- **边调试边重构**——两个未知变量，一次测量
- **静默的部分修复**——你机器上好了，是因为你顺手改了个无关的东西
- **无法执行的评审意见**（「建议改进错误处理」）——永远要说清输入、期望行为、证据

## 安装

把目录放进 Agent 的技能文件夹：

```bash
git clone https://github.com/Shine8592/code-quality-workflows.git
cp -r code-quality-workflows ~/.hermes/skills/software-development/
```

`SKILL.md` 的 frontmatter（`name`、`description`）是 Agent 运行时索引的依据；`references/` 目录按需加载。
